# 음승재 · 게임 프로그래머 포트폴리오

## Comet Foundry

**Unity 6 · C# · 우주 공장 경영 시뮬레이션**

혜성을 탐사하고 자원을 확보해 생산시설과 물류망을 확장하는 게임입니다. 이 포트폴리오는 프로젝트의 주요 시스템을 소개하고, 직접 작성한 `Assets/CometFoundry/TestScripts`의 구현과 검증 과정을 구분해 설명합니다.

## 1. 개인 구현 범위

직접 작성한 코드는 `TestScripts` 폴더입니다. 폴더명에 Test가 붙어 있지만, 내용은 혜성 생성과 보유 목록 관리 등을 구현하는 프로토타입입니다. NUnit 기반 자동 테스트와 구분합니다.

| 구분 | 범위 | 포트폴리오에서의 역할 |
| --- | --- | --- |
| 직접 작성한 코드 | `Assets/CometFoundry/TestScripts` | 개인 프로그래밍 구현의 근거 |
| 프로젝트 플레이어블 | `Assets/CometFoundry/Scripts` | 게임 전체의 시스템과 동작을 설명하는 참고 자료 |
| 자동 검증 코드 | `Assets/CometFoundry/Tests/EditMode` | 기존 프로젝트의 검증 자료. 개인 작성 범위에 포함하지 않음 |

현재 개인 구현은 혜성 데이터 모델, 후보 3개 생성, 등급에 따른 자원 설정, 선택·삭제, 관리자 호출 흐름과 타일 단위 건설 가능 여부 검사입니다. 생산·물류·거래·저장 시스템 전체를 직접 구현한 것으로 기재하지 않습니다.

## 3. 주요 개인 구현: 혜성 후보 생성

### 구현 목적

탐사할 때 서로 다른 데이터를 가진 혜성 후보를 생성하고, 이후 선택 기능에서 사용할 수 있도록 목록으로 반환합니다.

### 처리 흐름

1. `List<TestCometData>`를 생성합니다.
2. 반복문 안에서 매번 새로운 `TestCometData` 객체를 만듭니다.
3. ID와 이름을 설정하고 등급을 무작위로 정합니다.
4. 등급에 따라 자원 노드 수를 정합니다.
5. 노드마다 자원 종류와 자원량을 정하고 종류별 총량에 누적합니다.
6. 가로·세로 크기를 설정한 뒤 목록에 추가합니다.
7. 후보 3개가 담긴 목록을 반환합니다.

### 데이터 설정 규칙

| 항목 | 현재 코드의 규칙 |
| --- | --- |
| 후보 수 | 3개 |
| 후보 ID | 호출할 때마다 1·2·3 부여 |
| 등급 | 0~4 |
| 등급별 노드 수 | 등급 0·1·2·3·4에 각각 5·4·3·2·1개 |
| 노드 종류 | 철·구리·얼음 중 무작위 선택 |
| 노드별 자원량 | 2,500~4,999 |
| 가로·세로 | 각각 10~18 |

정수형 `Random.Range` 호출의 상한을 제외한 범위로 정리했습니다. 같은 자원 종류가 여러 노드에서 나올 수 있으며, 이 경우 해당 자원의 총량에 더합니다.

### 코드로 설명할 부분

```csharp
for (int i = 0; i < 3; i++)
{
    TestCometData comet = new TestCometData();
    comet.cometID = i + 1;
    comet.cometName = "comet - " + comet.cometID;
    comet.cometGrade = Random.Range(0, 5);
    // 등급별 노드 수와 노드별 자원량 설정
    comets.Add(comet);
}
```

원본의 핵심 흐름을 발췌했습니다. 새 객체를 반복문 안에서 생성해 후보별 데이터를 각각 보관합니다. 같은 객체를 계속 수정해 목록에 넣는 방식과 달리, 각 후보가 독립적인 필드 값을 갖습니다.

### 남은 과제

후보 ID는 탐사할 때마다 다시 1부터 시작하므로 전체 보유 목록에서 고유하지 않습니다. 후보의 무작위 생성이 서로 다른 결과를 반드시 보장하지는 않습니다. 고유 식별자 부여, 난수 시드를 이용한 재현, 후보 선택 이후 목록 갱신은 추가 개선 대상입니다.

## 4. 주요 개인 구현: 선택과 보유 목록 관리

`TestPlayerData`는 `List<TestCometData>`로 보유 혜성을 관리합니다. 생성 목록과 보유 목록을 나누고, 선택한 후보를 플레이어 목록에 추가하거나 보유 목록의 지정 인덱스를 삭제하는 함수를 작성했습니다.

- `selectSaveCometData()`는 선택 인덱스를 받아 후보 객체를 보유 목록에 추가합니다.
- `selectDeleteCometData()`는 인덱스를 검사한 뒤 `RemoveAt()`으로 해당 항목을 삭제합니다.
- `OnSelectButton()`과 `OnDeleteButton()`은 관리자에서 각 기능을 호출하는 진입점입니다.

여기서 Save는 메모리의 보유 목록에 추가한다는 의미입니다. 파일 저장이나 게임 종료 후 상태 복원은 이 코드의 구현 범위에 포함되지 않습니다.

### 현재 코드에서 확인한 오류

`selectSaveCometData()`에는 같은 `player.userComet.Add(comets[selectedIndex])` 호출이 두 번 있습니다. 유효한 입력이면 한 번의 선택으로 같은 객체 참조가 두 번 들어가는 구조입니다. 이후 하나를 삭제해도 다른 항목이 남을 수 있습니다.

또한 null 검사가 목록 접근과 첫 번째 추가보다 뒤에 있습니다. 검사를 작성했지만, null 입력에서는 검사에 도달하기 전에 예외가 발생할 수 있습니다.

### 개선 방향

인수의 null 여부, 보유 목록의 초기화, 선택 인덱스를 먼저 검사하고 모든 검사를 통과한 경우에 한 번만 추가하도록 정리해야 합니다. 같은 후보의 재선택 허용 여부도 정해야 합니다. 현재는 후보를 보유 목록에 참조로 추가하며, 후보 목록을 비우는 코드는 주석 상태입니다.

이 항목은 소스 검토로 찾은 개선 과제이며, 수정 완료 사례로 기재하지 않습니다.

## 5. 주요 개인 구현: 관리자와 컴포넌트 연결

`TestCometFoundryManager.Start()`에서 플레이어와 시작 혜성 데이터를 만들고, `GetComponent<TestCometGenerate>()`로 같은 GameObject의 생성기를 가져옵니다. 컴포넌트가 없으면 오류를 출력하고 초기화를 중단합니다.

현재 시작 흐름은 후보 생성, 두 번째 후보 선택, 로그 출력, 보유 목록 삭제를 호출하는 실습 형태입니다. 별도로 생성·선택·삭제 버튼에서 호출할 수 있는 public 메서드도 작성했습니다.

`OnGenerateButton()`은 생성기가 없을 때 경고를 출력하지만 반환하지 않고 다음 줄에서 생성기를 사용합니다. null 상태에서는 호출을 중단하도록 수정할 필요가 있습니다. 버튼 메서드가 있다는 사실만으로 실제 UI 연결과 실행 완료를 주장하지 않습니다.

## 6. 주요 개인 구현: 건설 그리드

`LoadBuildingGrid(width, length)`에서 `bool[,]` 배열을 만들고 각 타일을 비점유 상태로 초기화합니다. `CanBuild(x, y)`에서는 그리드 초기화 여부와 좌표 범위를 확인한 뒤 해당 타일이 비어 있는지 반환합니다.

```csharp
public bool CanBuild(int x, int y)
{
    if (buildingGrid == null) return false;

    if (x < 0 || y < 0 ||
        x >= buildingGrid.GetLongLength(0) ||
        y >= buildingGrid.GetLongLength(1))
        return false;

    return !buildingGrid[x, y];
}
```

현재 구현은 한 타일의 건설 가능 여부 검사입니다. 건물 크기 전체의 검사, 건설 시 점유 변경, 철거 시 해제, 비용 차감, Prefab 배치는 아직 구현되지 않았습니다. `TestBuildingData`에 정의한 가로·세로 정보를 배치 검사에 연결하는 것이 다음 과제입니다.

## 7. 개인 구현의 테스트·검증 부분

### 기존 실습 기록

`Test 기술서.md`에는 혜성 기본 객체 생성 성공과 객체별 무작위 값 부여 실패가 기록되어 있습니다. 현재 소스에는 후보마다 객체를 생성하고 무작위 값을 넣는 코드가 있지만, 해당 변경 후 실행 결과는 이번 검토에서 재확인하지 않았습니다.

현재 `TestScripts`의 확인 방식은 주로 `Debug.Log`입니다. 이 폴더에 자동 assertion 테스트 메서드는 없으며, `using NUnit.Framework`가 있다는 사실만으로 자동 테스트를 작성했다고 보지 않습니다.

### 추가로 검증할 항목

아래는 검증 계획입니다. 이번 작성 과정에서 실행한 결과가 아닙니다.

| 대상 | 확인 방법 | 기대 결과 |
| --- | --- | --- |
| 후보 생성 | 생성 후 목록 수와 객체 참조 확인 | 후보 3개, 서로 다른 객체 참조 |
| 등급과 노드 | 여러 생성 결과의 등급·노드 수 비교 | 등급 0~4, 매핑된 노드 수 일치 |
| 자원 누적 | 노드 종류와 종류별 자원량 확인 | 활성 노드 수만큼 자원량 합산 |
| 후보 크기 | 가로·세로 확인 | 각각 10~18 |
| 선택 | 유효한 후보를 한 번 선택 | 보유 수가 정확히 1 증가. 현재 중복 추가 수정 필요 |
| 잘못된 입력 | null, 음수·범위 초과 인덱스 전달 | 예외 없이 거절하고 목록 유지. 현재 검사 순서 개선 필요 |
| 삭제 | 보유 목록 중 한 항목 삭제 | 선택 항목만 제거, 보유 수 1 감소 |
| 건설 검사 | 초기화 전·범위 밖·유효 좌표 검사 | 잘못된 좌표 거절, 초기 빈 타일 허용 |

자동 테스트를 추가한다면 무작위 값 자체가 매번 다르다는 검증보다 값의 범위와 데이터 관계를 확인하는 것이 적절합니다. 같은 난수 결과가 나오는 것은 정상일 수 있습니다.

## 8. 프로젝트 전체의 주요 시스템 설명

다음은 기존 플레이어블의 시스템 설명입니다. 개인 구현 근거인 `TestScripts`와 별도 범위입니다.

| 시스템 | 역할과 핵심 규칙 | 대표 코드 |

### 개인 구현과의 연결

직접 만든 혜성 데이터와 후보 목록은 탐사·보유 혜성 관리의 기본 구조에 해당합니다. 건설 그리드 실습은 시설 배치의 좌표·점유 검사를 준비하는 단계입니다. 이후 후보 선택 UI와 건물 크기 검사, 점유 처리를 연결해 작은 플레이 흐름을 완성할 수 있습니다.

기존 자동 테스트 수나 물류 개선 성과는 위 시스템의 참고 기록입니다. 이를 개인 작성 코드의 성과나 개인 테스트 실적으로 옮기지 않습니다.

## 9. 다음 구현 목표

1. 선택 함수의 중복 추가와 null 검사 순서를 수정합니다.

6. 생성·선택·삭제·배치의 정상·실패 조건을 자동 테스트로 검증합니다.

현재 코드에 있는 `UnityEditor` 및 테스트 관련 using의 빌드 영향도 확인할 필요가 있습니다. 이번 작업은 포트폴리오 문서 수정이며 소스 수정이나 Unity 실행·빌드는 수행하지 않았습니다.

## 10. 면접에서 설명할 개인 구현 요약

> C#으로 혜성 데이터와 플레이어의 보유 목록을 만들고, 후보 세 개를 생성하는 프로토타입을 작성했습니다. 후보마다 새 객체를 생성하고 등급에 따라 자원 노드 수를 정한 뒤, 무작위 자원량을 종류별로 누적하도록 구현했습니다. 선택과 삭제는 List로 관리하고, 관리자가 생성기 컴포넌트를 가져와 호출하도록 구성했습니다. 건설은 2차원 배열과 좌표 범위를 이용한 단일 타일 검사까지 작성했습니다. 현재는 선택 시 중복 추가와 입력 검사 순서를 개선하고, 건물 크기를 반영한 배치 처리와 자동 테스트를 추가하는 단계입니다.
